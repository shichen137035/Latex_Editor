# TeXWeave LaTeX project

- Treat the working copy as a LaTeX project. Its `.tex` files are the content source of truth; `.texweave/structure.json` is only a structural index, not a second document.
- Locate first: use `list_blocks` or `find_blocks` (type, title/query, label, actual compiled number, or ordinal). Inspect with `get_block` / `get_blocks`, then call `get_block_source` only for the blocks needed. Do not read entire papers when block APIs can locate the target. For “edit theorem prose, keep formulas”, inspect the theorem's children and read/edit its paragraphs, leaving equation children untouched.
- Use `replace_block_content` for content blocks, with the exact source returned by `get_block_source` and its `revision` as `expectedRevision`. For environment-backed content, preserve the returned wrapper and labels. Structural blocks have no direct editable body: edit their content children instead. An empty structural block exposes a placeholder paragraph; filling it materializes the paragraph.
- Use `insert_block` for typed insertions (heading `title` is separate from body `content`). Supply `fileId` for root insertion in multi-file projects. `delete_block` deletes the complete subtree, not just the wrapper; only delete content the user asked to remove.
- On `STALE_BLOCK`, refetch the target and reconcile the newer source instead of retrying an old replacement. Preserve user changes. A content block with children produces a nonfatal warning, not permission to flatten or rewrite it. Use `set_block_semantic` to add summaries or AI-owned tags through the block API; treat stale metadata as a hint, not authority.
- Block tools and shell edits modify the same reviewable working copy. Use normal file edits for preambles, bibliography/style files, or operations outside the block API; inspect only the relevant files. Treat `.texweave/structure.json` as a derived index, not a routine edit target: use block tools for source changes and `set_block_semantic` for summaries or tags. Direct structure edits are reserved for cases where the user explicitly asks to repair that metadata file; review them manually and preserve its schema and unrelated metadata. Do not edit other `.texweave` or `.latex-editor` internal files. Changes remain subject to TeXWeave's existing diff review and undo workflow.
- Preserve the project's language, document class, package choices, citation style, labels, and existing structure. Keep edits focused on the user's request.
- Logical dependencies use one direction: `source → target` means the target depends on the source. Only relation-capable structural/semantic blocks participate; paragraphs, formulas, figures, tables and lists cannot be endpoints. Use the existing structural `placeholder` virtual block when an ordinary-looking logical unit needs an independent identity; its markers have no PDF effect.
- Prefer `relation_get_scope` or `relation_get_logic_context` to select relevant prerequisites/dependents, and `relation_get_display_scope` to include contained content or structural parents. Read actual source with block tools. Multiple focuses use union and distances come from the shared backend; do not invent a separate traversal or infer logical relations from textual citations.
- Use `relation_propose_create`, `relation_propose_delete` and `relation_propose_reverse` for relation edits. Each validated proposal requires explicit approval before it enters the persistent graph, including full access mode. Do not modify `relations` or the legacy `dependencies` projection in metadata files: file diffs cannot commit relation changes. New source blocks must be accepted into the project before they can be linked. On a stale or invalid proposal, refetch the relevant blocks/relations and produce a fresh proposal.
- Keep `\begin{...}` and `\end{...}` pairs balanced. Preserve existing labels and references; update references when a requested edit changes them.
- When a build check is useful, call the TeXWeave `texweave_compile` tool. It runs the configured compiler on the AI working copy and returns build diagnostics. Do not run `latexmk`, `pdflatex`, `xelatex`, `lualatex`, `tectonic`, `arara`, `bibtex`, or `biber` through a shell; TeXWeave owns compilation and its build settings.
- Use reported file and line locations to repair LaTeX errors, then call `texweave_compile` again when appropriate. Explain any unresolved errors or warnings in the final response.
- Do not edit compiler-generated files such as `.aux`, `.log`, `.fls`, `.fdb_latexmk`, `.synctex.gz`, `.xdv`, or build-directory output as source content.
- Summarize source files changed and whether the TeXWeave build succeeded.
