# TeXWeave 0.6.7 发布前校验与封包评估

日期：2026-10-12。目标版本为 0.6.7；根 `package.json` 与锁文件的版本号现已统一更新。本轮没有构建发行产物、生成安装包或发布文件。

根据用户最新要求，现有 NSIS 安装方式视为待替换的历史实现。下面列出的旧安装器问题用于约束重建方案，不建议逐项继续修补旧安装器。

Vitest 最初因 Windows 沙箱阻断 `realpathSync.native` 而无法启动；在正常执行权限下完整运行后得到以上结果。它是本次执行环境限制，不是 TeXWeave 的功能故障。单元测试耗时约 3.77 秒，集成测试约 1.35 秒，仅代表本次机器与并行设置。

本轮没有运行真实 LaTeX 编译器、CLI 端到端、Electron 交互回归、安装器、干净虚拟机、长期内存测试或依赖漏洞扫描。未对未生成的安装包作出验证结论。

## 正式发布前的必要处理

### 1. 使发布检查真正通过

- 上述 2 个 lint 错误已修复；仍需更新 2 个过时的本地化测试。
- 修正实际串语言文本。例如 `ui.environments.invalid_or_duplicate_preview_environment_id` 在 `fr.json` 中是日语，在 `ja.json` 中是法语。法语目录有 20 个含日文假名或汉字的条目，需要逐条核对，不能仅凭脚本命中就认定全部错误。
- 在指定工具链上运行真实编译测试，包括多文件 PDF、图片、参考文献、交叉引用及 SyncTeX。现有编译器测试在缺少工具链时会跳过；正式发布门槛必须明确拒绝“核心编译场景全部跳过但整体绿灯”。
- 对最后确定的源代码修订运行 Electron 回归，并保存结果及失败诊断。

### 2. 建立从干净源码到产物的可追溯流程

当前工作区包含大量未提交修改和新文件，发布时必须把所需文件完整纳入一个确定的修订，并记录版本、修订号、工具链版本和锁文件信息。

已确认存在过时输出：`apps/desktop/src/main/ai/tex-dependencies.ts` 已删除，而 `apps/desktop/dist/main/ai/tex-dependencies.js` 仍存在。当前构建只清空 renderer 输出，主进程和工作区包的 TypeScript 输出会保留删除文件的旧产物；广泛的 `dist/**/*` 封包规则可能继续收录它。

新流程应从干净检出和锁文件安装开始，清理限定范围内的生成目录及增量构建状态，再构建一次。后续桌面验证和封包复用这次产物，避免边检查边反复改变待发布内容。建议建立 Windows CI 或等效的隔离构建机。

### 3. 验证最终包的运行依赖

当前 `verify:release` 与 `desktop:dist:win` 分开：前者没有最终包检查，后者没有完整质量检查。`verify-package.cjs` 主要检查文件存在、版本和包目录，没有真正启动 `win-unpacked`。

重建时应维护明确的运行包和资源清单，剔除 `test-support` 等测试用途的工作区包及无关源码。已有 verifier 会遍历所有 `packages` 并要求收录，不能直接作为新的运行依赖清单。

重点验证 SQLite、Copilot SDK 的原生运行时及 `koffi`、PDF.js worker、数学渲染、词典、语言目录、主题与默认项目资源，特别是 ASAR 内外路径和原生文件加载。electron-builder 具有生产依赖收集和原生模块解包机制，但仍需要最终产物的加载测试；参见 [electron-builder v26 配置](https://www.electron.build/v26/docs/configuration/) 和 [应用文件说明](https://www.electron.build/docs/contents/)。

AI 的一键安装也有独立前提：目前 Codex/Copilot CLI 安装代码使用系统 Node/npm；Electron 内置 Node 并不会使系统 PATH 自动拥有 npm。必须决定是提供受版本与完整性校验约束的独立运行时下载，还是明确列出外部前提并可靠降级。Copilot SDK 自带运行时和另行安装的登录 CLI也需要分别验证。

### 4. 重建安装与用户数据规则

建议首个发行目标继续限定 Windows x64。新安装器首先只负责应用、快捷方式及明确的文件关联；外部 TeX、可选词典和 AI 运行时通过真实可用的首次运行或设置流程管理。

旧实现提示了以下约束：

- 安装器的“语言包 / 拼写 / LaTeX”选项主要写入请求记录，没有看到消费这些请求并改变实际功能的链路；选择语言也没有接入应用的 `settings.locale`。新安装器每个选项都应有可验证的效果。
- 安装器语言表仍只有 6 种，遗漏哈萨克语；界面名称与语言代码应区分。
- 旧元数据将 `$INSTDIR` 直接写进 JSON，Windows 反斜杠没有 JSON 转义；该文件也没有读取入口。重建时统一用有明确定义的交接格式，或取消无用途的元数据。
- 应明确卸载保留/清理的对象：设置、注册表、文献库、AI 会话及附件、样式资源、托管工具和缓存。默认保留用户数据；任何清理都不得触及用户项目或外部 TeX 安装。
- 当前便携可执行文件仍使用 AppData 用户目录。必须明确它表示“无需安装”，还是也要求用户数据随文件夹携带。

干净 Windows 账户/虚拟机需至少检查：无 Node/npm、无 TeX 时能启动与正常编辑；安装 TeX 后能编译；中文和空格路径；只读/缺失资源；启动、重开项目、更新覆盖安装、取消安装、卸载及用户数据保留。测试对象必须是最终包，不是开发脚本。

### 5. 补齐对外发行材料

- 仓库目前没有项目 LICENSE/许可说明及统一第三方声明。发布前确定自有代码授权方式，并清点实际分发的 Electron、SDK、词典及其他第三方材料。
- `apps/desktop/build` 品牌资源目录目前不存在，封包配置也未设置产品图标；补齐 EXE/安装器图标、发布者信息、发行说明、系统要求和已知限制。
- 明确发布位置、问题反馈方式、应用诊断日志的获取方式以及更新/重新安装流程。
- 对发布文件生成 SHA-256 和产物清单。代码签名建议纳入公开正式发行计划；若先发未签名测试版，应清楚标明。签名用途见 [Electron 官方说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)。
- 扫描锁定的依赖与 Electron 版本的安全状态，再确定发行用工具链。不能用此次类型检查推断没有依赖漏洞。
- 从首个对外版本开始制定设置、结构、历史和文献数据的格式版本与升级策略；目前未发布的旧格式无需为其建立永久兼容层。

## 建议的 0.6.7 构建与封包顺序

1. 修复检查失败、核对译文，确定 Windows x64 的发行范围与运行依赖策略。
2. **已完成：**更新根 `package.json` 和锁文件的根版本为 0.6.7；首页和运行时继续读取唯一版本来源，不另设 UI 版本常量。
3. 冻结修订，干净安装依赖，完成静态、单元、服务集成和指定工具链验证。
4. 清理生成目录，构建一次生产 renderer、main、preload 和必要运行包。
5. 组装隔离的封包目录，校验版本、依赖、资源与原生文件；先生成未安装的应用目录并进行真实启动/功能检查。
6. 使用现有 electron-builder 工具重建安装配置，生成安装版及按产品定义选择的便携产物。
7. 完成干净机器上的安装、覆盖更新、卸载与数据保留测试。
8. 生成签名（若采用）、校验和、许可声明、发行说明及验证报告后再发布。

自动更新、macOS/Linux、用户 JS/TS 块插件和云工作区可以排到后续版本，不必为首个 Windows 发行版扩展这些功能。当前主要缺口在可重复构建、最终产物验证和对外发行约定；功能数量已经不是当前发布准备的主要限制。
