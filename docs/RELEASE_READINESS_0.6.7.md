# TeXWeave 0.6.7 发布前校验与封包评估

日期：2026-10-13。目标版本为 0.6.7；根 `package.json` 与锁文件的版本号现已统一更新。本轮已搭建并实际运行 Windows x64 便携版封包流程；安装器和发布仍未包含在内。

旧 NSIS 安装方式及未接入运行功能的组件选择脚本已清理。当前只提供无需安装的便携版；安装、更新、文件关联和用户数据迁移规则确定后，再单独设计安装器。

## 2026-10-12 仓库清理

已移除旧安装清单、TeX Live 安装配置和 PowerShell 安装脚本，以及已过时的安装生命周期文档。发行封包不再复制安装器元数据；过期检查报告和旧实施路线图也已清理。新增的 `clean:build` 会在生产构建前清理工作区 `dist` 和 `.tsbuildinfo`；`.tmp` 与 release 产物继续作为生成文件处理。

清理后首次源码校验发现 13 个旧 `.tsbuildinfo` 仍在各项目目录中，TypeScript 因此误以为已删除的 `dist` 输出仍然有效，未重建 contracts 子路径声明。清掉增量状态后，干净源码构建通过。以后清理编译输出时必须同时清理工作区的 `.tsbuildinfo`；不要只删 `dist`。

## 正式发布前的必要处理

### 1. 使发布检查真正通过

- **已关闭：**更新 2 个已过期的本地化测试断言，并修正法语目录中确认误入的 20 条日文/中文文案。
- **已通过本机工具链：**运行 latexmk 编译和 SyncTeX 实测。发行构建环境仍应确认这些测试没有因工具链缺失而跳过。
- 对最后确定的源代码修订运行 Electron 回归，并保存结果及失败诊断。

### 2. 建立从干净源码到产物的可追溯流程

当前工作区仍含未提交修改；正式发布需先冻结一个明确修订，并记录版本、提交号、工具链与锁文件信息。生产构建现会先运行 `clean:build` 清理旧 `dist` 和 `.tsbuildinfo`，再重新生成 renderer、main、preload 与工作区包。正式发行建议在干净检出上通过 `npm ci` 重跑全流程，并建立 Windows CI 或隔离构建机。

### 3. 验证最终包的运行依赖

`desktop:dist:win` 现先运行 `verify:release`，再构建便携包并校验版本、归档入口、工作区运行包、必要资源和便携产物。`test-support` 已明确排除。当前 verifier 检查包内容但不会启动 `win-unpacked`，所以干净用户账户下的首次启动和实际功能验证仍需补做。

重点验证 SQLite、Copilot SDK 的原生运行时及 `koffi`、PDF.js worker、数学渲染、词典、语言目录、主题与默认项目资源，特别是 ASAR 内外路径和原生文件加载。electron-builder 具有生产依赖收集和原生模块解包机制，但仍需要最终产物的加载测试；参见 [electron-builder v26 配置](https://www.electron.build/v26/docs/configuration/) 和 [应用文件说明](https://www.electron.build/docs/contents/)。

AI 的一键安装也有独立前提：目前 Codex/Copilot CLI 安装代码使用系统 Node/npm；Electron 内置 Node 并不会使系统 PATH 自动拥有 npm。必须决定是提供受版本与完整性校验约束的独立运行时下载，还是明确列出外部前提并可靠降级。Copilot SDK 自带运行时和另行安装的登录 CLI也需要分别验证。

### 4. 重建安装与用户数据规则

首个发行目标当前限定 Windows x64 便携版。后续若加入安装器，应先明确快捷方式、文件关联、更新和外部运行时的交互；每个安装选项都需要可验证的效果。

旧实现提示了以下约束：

- 已删除的旧安装实现曾包含没有消费链路的语言/拼写/LaTeX 选择、缺少哈萨克语的语言表和未读取的路径元数据；新实现不再携带这些无效选项。
- 若提供安装/卸载，应明确设置、文献库、AI 会话、附件、样式、托管工具及缓存的保留规则；任何清理都不得触及项目文件或外部 TeX 安装。
- 当前便携版的设置仍保存在 Electron 用户数据目录。需要决定未来是否改为随程序目录携带。

干净 Windows 账户/虚拟机需至少检查：无 Node/npm、无 TeX 时能启动与正常编辑；安装 TeX 后能编译；中文和空格路径；只读/缺失资源；项目重开及用户数据保留。测试对象必须是最终包，不是开发脚本。

### 5. 补齐对外发行材料

- 仓库目前没有项目 LICENSE/许可说明及统一第三方声明。发布前确定自有代码授权方式，并清点实际分发的 Electron、SDK、词典及其他第三方材料。
- 封包目前使用 Electron 默认图标，根清单尚未声明 author；补齐产品图标、发布者信息、发行说明、系统要求和已知限制。
- 明确发布位置、问题反馈方式、应用诊断日志的获取方式以及更新/重新安装流程。
- 对发布文件生成 SHA-256 和产物清单。代码签名建议纳入公开正式发行计划；若先发未签名测试版，应清楚标明。签名用途见 [Electron 官方说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)。
- 扫描锁定的依赖与 Electron 版本的安全状态，再确定发行用工具链。不能用此次类型检查推断没有依赖漏洞。
- 从首个对外版本开始制定设置、结构、历史和文献数据的格式版本与升级策略；目前未发布的旧格式无需为其建立永久兼容层。

## 建议的 0.6.7 构建与封包顺序

1. 修复检查失败、核对译文，确定 Windows x64 的发行范围与运行依赖策略。
2. **已完成：**更新根 `package.json` 和锁文件的根版本为 0.6.7；首页和运行时继续读取唯一版本来源，不另设 UI 版本常量。
3. 冻结修订，在干净 Windows 检出运行 `npm ci` 与 `npm run desktop:dist:win`。
4. 发布流程会清理生成目录、重建桌面产物、运行静态与自动化检查，并生成便携包。
5. 在干净 Windows 账户/虚拟机启动最终便携包，检查 TeX 检测、项目编辑和 PDF 预览。
6. 处理图标、author、代码签名（若采用）、许可声明、校验和、发行说明及反馈渠道后再公开发布。

自动更新、macOS/Linux、用户 JS/TS 块插件和云工作区可以排到后续版本。当前本机可重复构建和便携封包流程已建立；下一步重点是干净账户启动验证及对外发行材料。
