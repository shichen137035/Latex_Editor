# 本地 LaTeX 编辑器 v0.1 技术要求与调试测试规格

> 文档状态：可直接作为 Codex 实现任务的技术合同  
> 目标版本：v0.1  
> 技术栈：Electron + React + TypeScript + Monaco Editor + Node.js + `latexmk`  
> 核心原则：本地优先、无前端可调试、数据驱动、模块可替换、危险操作显式确认

## 1. 文档目的

本规格定义本地 LaTeX 编辑器 v0.1 的架构、模块边界、接口、数据模型、命令行调试入口、自动化测试、验收标准和后续扩展点。

实现者应把本文件中的 **MUST / MUST NOT / SHOULD / MAY** 分别理解为“必须 / 禁止 / 建议 / 可选”。若实现与本规格冲突，应先更新技术决策记录（ADR）并解释原因，不能静默偏离。

v0.1 的核心交付不是完整图形界面，而是一套能够被 CLI、自动化测试和未来 Electron UI 共同调用的稳定核心服务。

## 2. v0.1 目标与非目标

### 2.1 目标

v0.1 MUST 完成以下闭环：

1. 注册现有本地文件夹或创建新的本地 LaTeX 项目。
2. 浏览项目内文件，读取、修改并安全保存文本文件。
3. 维护编辑缓冲区状态，包括 `clean`、`dirty` 和 `externallyModified`。
4. 指定项目主文件，并通过 `latexmk` 发起编译。
5. 返回结构化编译结果，至少包含成功状态、PDF 路径、错误和警告。
6. 创建带标签的项目版本快照，列出快照，并安全恢复旧版本。
7. 从项目列表移除项目时，区分“只移除注册记录”和“删除本地文件夹”。
8. 在没有 React/Monaco 前端的情况下，通过 CLI 和自动化测试验证全部核心流程。
9. 将补全词典、snippet、LaTeX 命令元数据、环境元数据等非逻辑内容保存在可编辑、可验证的数据资源中，而不是散落在 TypeScript 源码里。

### 2.2 非目标

以下内容不属于 v0.1 必须交付范围：

- 完整视觉设计和正式 UI。
- 多人实时协作、云同步或账户系统。
- 完整 LaTeX 语言服务器协议实现。
- 所见即所得编辑。
- 全量 TeX Live/MiKTeX 安装管理。
- Git 托管、远程仓库同步或分支管理。
- PDF SyncTeX 双向跳转的正式 UI；可预留接口。
- 复杂文件拖拽、插件市场和第三方扩展运行时。

## 3. 总体架构约束

### 3.1 分层结构

系统 MUST 至少划分为以下层次：

```text
React + Monaco Renderer
          │
          │ typed preload API
          ▼
Electron Preload / IPC Adapter
          │
          ▼
Application Services
          │
          ├── ProjectService
          ├── DocumentService
          ├── CompilerService
          ├── DiagnosticService
          ├── VersionService
          └── ResourceCatalogService
          │
          ▼
Domain + Infrastructure Adapters
          ├── Local filesystem
          ├── SQLite project registry
          ├── JSON/XML resource files
          ├── Process runner (`latexmk`)
          └── Clock / IDs / hashing
```

核心包 MUST NOT import `electron`、`react`、`monaco-editor` 或浏览器 DOM API。Electron、CLI 和测试只能通过公开应用服务调用核心能力。

### 3.2 依赖方向

依赖只能由外向内：

```text
renderer -> preload/ipc -> application -> domain
cli ---------------------> application -> domain
infrastructure -------------------------> domain ports
```

Domain 层 MUST NOT 直接依赖 SQLite、Node `fs`、Electron 或具体进程实现。文件系统、数据库、进程启动、时钟和 ID 生成都应通过 port/interface 注入，以便测试替换。

### 3.3 工作线程与进程边界

- Renderer MUST NOT 获得任意文件系统或进程权限。
- `nodeIntegration` MUST 为 `false`，`contextIsolation` MUST 为 `true`。
- Preload 只能暴露白名单 API，不得暴露原始 `ipcRenderer`。
- 编译必须发生在 Electron main process 或独立 worker 中，不能阻塞 renderer。
- CLI 与 Electron MUST 复用同一套 application service，不得复制业务逻辑。

## 5. Source Editor 核心与 Monaco 集成边界

### 5.1 Editor Core 职责

`editor-core` MUST 是纯 TypeScript 模块，不依赖 Monaco。它负责：

- 文档标识、URI/路径映射和文本版本号。
- 打开、修改、保存、关闭文档的状态机。
- dirty state 与外部修改检测。
- 基础 LaTeX 扫描：命令、环境、`\label`、`\ref`、`\cite`、`\input`/`\include`。
- 从 `ResourceCatalogService` 查询补全、snippet、命令和环境元数据。
- 把编辑器无关的补全项、文档符号和诊断转换为统一 contract。
- 保存前校验和冲突处理。

v0.1 的解析器允许是容错的轻量扫描器，不要求完整 TeX AST；但遇到不完整命令、注释和转义字符时不得崩溃。

### 5.2 Monaco Adapter 职责

`apps/desktop/src/renderer` 中的 Monaco adapter 只负责：

- 创建和释放 Monaco model。
- 将 Monaco `ITextModel` 的改变转换为 `DocumentService.applyChanges`。
- 将核心补全项映射为 Monaco completion item。
- 将核心诊断映射为 Monaco marker。
- 注册快捷键、保存动作、语言配置和 UI provider。
- 将 model version 与核心文档 revision 对齐。

Monaco adapter MUST NOT：

- 直接读写本地文件。
- 直接调用 `latexmk`。
- 自己维护项目注册信息。
- 内置 LaTeX 命令表、snippet 表或环境表。
- 承担可由 `editor-core` 独立测试的解析逻辑。

### 5.3 文档状态模型

```ts
export type DocumentStatus =
  | "clean"
  | "dirty"
  | "externallyModified"
  | "deletedOnDisk";

export interface OpenDocument {
  projectId: string;
  relativePath: string;
  encoding: "utf8";
  content: string;
  revision: number;
  diskHash: string;
  status: DocumentStatus;
  openedAt: string;
  lastSavedAt?: string;
}
```

保存 MUST 使用以下冲突规则：

1. 打开文件时记录内容哈希或等价版本标识。
2. 保存前再次读取磁盘状态。
3. 若磁盘内容已变化，返回 `EXTERNAL_MODIFICATION_CONFLICT`，不得静默覆盖。
4. 调用方必须显式选择重新载入、另存或强制覆盖。
5. v0.1 CLI 可提供 `--force`，但默认不得覆盖。

### 5.4 Source Editor 公开接口

```ts
export interface DocumentService {
  open(input: OpenDocumentInput): Promise<OpenDocument>;
  applyChanges(input: ApplyTextChangesInput): Promise<OpenDocument>;
  save(input: SaveDocumentInput): Promise<SaveDocumentResult>;
  reload(input: DocumentRef): Promise<OpenDocument>;
  close(input: CloseDocumentInput): Promise<void>;
  listOpen(projectId: string): Promise<OpenDocumentSummary[]>;
}

export interface EditorIntelligenceService {
  getCompletions(input: CompletionRequest): Promise<CompletionItem[]>;
  getDocumentSymbols(input: DocumentText): Promise<DocumentSymbol[]>;
  getProjectReferences(projectId: string): Promise<ProjectReferenceIndex>;
}
```

`ApplyTextChangesInput` SHOULD 使用带 range 的增量变更；v0.1 可在 adapter 内退化为全文替换，但 contract 不应把未来实现锁死为全文模式。

## 6. Compiler 与诊断解析

### 6.1 编译流程

`CompilerService` MUST：

1. 验证项目和主文件存在。
2. 验证主文件位于项目根目录之内。
3. 从配置解析 `latexmk` 可执行文件及允许参数。
4. 使用参数数组启动进程，`shell: false`；禁止字符串拼接 shell 命令。
5. 将工作目录设置为项目根目录。
6. 捕获 stdout、stderr、退出码、超时和取消信号。
7. 优先启用适合解析的输出，例如 `-file-line-error`、`-interaction=nonstopmode`。
8. 将原始日志交给 `DiagnosticService`，返回结构化结果。
9. 检查预期 PDF 是否实际生成；仅退出码为 0 不足以判定完整成功。

建议默认命令语义：

```text
latexmk -pdf -file-line-error -interaction=nonstopmode -synctex=1 <main-file>
```

实际参数 MUST 来自经过 schema 校验的 toolchain 配置，并由代码中的 allowlist 限制危险参数。配置文件不能获得任意 shell 执行能力。

### 6.2 编译接口

```ts
export interface CompilerService {
  compile(input: CompileInput): Promise<CompileResult>;
  cancel(compilationId: string): Promise<CancelResult>;
  clean(input: CleanBuildInput): Promise<CleanBuildResult>;
  detectToolchain(): Promise<ToolchainStatus>;
}

export interface CompileInput {
  projectId: string;
  mainFile?: string;
  mode?: "pdf";
  timeoutMs?: number;
}

export interface CompileResult {
  compilationId: string;
  status: "succeeded" | "failed" | "cancelled" | "timedOut";
  exitCode: number | null;
  startedAt: string;
  finishedAt: string;
  durationMs: number;
  mainFile: string;
  pdfPath?: string;
  logPath?: string;
  diagnostics: Diagnostic[];
  stdoutTail: string;
  stderrTail: string;
}
```

### 6.3 诊断模型

```ts
export interface Diagnostic {
  severity: "error" | "warning" | "info";
  source: "latex" | "latexmk" | "bibtex" | "biber" | "system";
  code?: string;
  message: string;
  file?: string;       // 项目相对路径
  line?: number;       // 1-based
  column?: number;     // 1-based
  endLine?: number;
  rawExcerpt?: string;
}
```

诊断解析 MUST 至少覆盖：

- `file.tex:line: ...` 形式的错误。
- `! Undefined control sequence.` 等 TeX 错误及后续 `l.<line>`。
- 缺少文件或 package。
- undefined references/citations。
- overfull/underfull box 警告。
- `latexmk` 找不到、无执行权限、超时和非零退出码。

无法识别的日志不得导致解析失败。解析器应保留原始日志路径和有限长度的 stdout/stderr tail，供调试使用。

### 6.4 安全与资源限制

- 路径输入 MUST 经过 canonicalization，并验证仍位于项目根目录内。
- 编译参数 MUST 使用数组传递，禁止 `shell: true`。
- 默认超时 SHOULD 为 120 秒，并允许项目级覆盖到安全上限。
- stdout/stderr 内存缓冲必须有限制；完整输出应流式写入日志文件。
- v0.1 应明确提示：LaTeX 本身可能执行危险操作；默认 MUST 禁止 `-shell-escape`。
- 若未来允许 shell escape，必须设计独立的信任提示和项目级授权，不得由资源文件静默开启。

## 7. Project Manager

### 7.1 项目定义

项目等同于用户选择的一个真实本地文件夹。应用不会把源文件导入私有数据库；保存操作直接写回该文件夹。

SQLite 项目注册表只保存索引和应用级元数据，不保存项目源文件正文。

### 7.2 项目能力

`ProjectService` MUST 支持：

- `registerExistingFolder`
- `createProject`
- `getProject`
- `listProjects`
- `openProject`
- `updateProject`
- `removeFromRegistry`
- `deleteLocalProject`
- `setMainFile`
- `touchEditedAt`

注册现有项目时 MUST：

- 检查路径存在且是文件夹。
- 解析为规范绝对路径。
- 检查重复注册；Windows 下比较时需要考虑大小写不敏感。
- 检查基本读权限，并单独报告写权限状态。
- 不修改项目内容，除非用户随后明确启用项目配置或版本快照功能。

创建项目时 MUST：

- 只在用户指定的父目录下创建明确的项目子目录。
- 默认生成 `main.tex`；模板内容来自模板资源文件，不得写死在命令处理器中。
- 若目标目录非空或已存在，默认失败，不得覆盖现有文件。

### 7.3 项目数据模型

应用级 SQLite 表建议如下：

```sql
CREATE TABLE projects (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  canonical_path TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL,
  registered_at TEXT NOT NULL,
  last_opened_at TEXT,
  last_edited_at TEXT,
  main_file TEXT,
  writable INTEGER NOT NULL DEFAULT 1,
  missing INTEGER NOT NULL DEFAULT 0,
  settings_json TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE schema_migrations (
  version INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL
);
```

要求：

- 时间使用 ISO 8601 UTC 字符串。
- `main_file` 必须是项目相对路径。
- 数据库 schema 修改必须通过顺序 migration，禁止运行时临时猜测字段。
- `settings_json` 只用于低频、可选的项目注册设置；需要查询或约束的数据应升级为正式列/表。
- 项目文件夹被移动或删除时，记录保留并标记 `missing = 1`，不得自动删除注册信息。

项目内可选配置建议保存在：

```text
<project>/.latex-editor/project.json
```

示例：

```json
{
  "$schema": "https://local.invalid/latex-editor/project.schema.json",
  "schemaVersion": 1,
  "mainFile": "main.tex",
  "compilerProfile": "latexmk-pdf",
  "autoSave": false,
  "snapshotExcludes": [".latex-editor/versions/**", "*.aux", "*.log", "*.pdf"]
}
```

应用级注册信息是“这台机器记住了哪些项目”；项目内配置是“项目如何构建”。两者 MUST NOT 混为一个文件。

### 7.4 文件服务

`ProjectFileService` MUST 支持：

```ts
export interface ProjectFileService {
  listTree(projectId: string): Promise<ProjectTreeNode[]>;
  readText(ref: ProjectFileRef): Promise<TextFileContent>;
  writeText(input: WriteTextFileInput): Promise<FileWriteResult>;
  createFile(input: CreateEntryInput): Promise<void>;
  createDirectory(input: CreateEntryInput): Promise<void>;
  rename(input: RenameEntryInput): Promise<void>;
  remove(input: RemoveEntryInput): Promise<void>;
}
```

所有接口都应接收项目相对路径，并在基础设施层解析与校验。必须防止 `..`、绝对路径、符号链接/junction 逃逸项目根目录。

文本写入 SHOULD 使用“同目录临时文件 + rename”的原子替换策略。v0.1 统一支持 UTF-8；检测到不兼容编码时应返回明确错误，不得乱码覆盖。

### 7.5 删除策略

删除必须明确区分两个动作：

#### A. 只从项目列表移除

- 删除 SQLite 中的注册记录。
- MUST NOT 修改本地项目文件夹。
- 这是默认和推荐操作。

#### B. 删除本地项目文件夹

- 同时删除注册记录和真实项目目录。
- 必须要求调用方传入独立、明确的确认字段，例如项目名称或 canonical path。
- 必须再次解析并验证目标路径与已注册路径完全一致。
- MUST 拒绝删除文件系统根目录、用户主目录、工作区上级目录和不再匹配的路径。
- SHOULD 优先使用系统回收站；若当前平台或运行环境无法恢复，必须在执行前把 `recoverable: false` 返回给 UI/CLI。
- 删除失败时不得先丢失注册记录；应保留或恢复注册状态并报告部分失败。

建议接口：

```ts
export type RemoveProjectRequest =
  | { projectId: string; mode: "registryOnly" }
  | {
      projectId: string;
      mode: "deleteLocalFolder";
      confirmedCanonicalPath: string;
    };
```

CLI 的本地删除必须同时要求 `--delete-local` 与 `--confirm-path <absolute-path>`；单独一个 `--force` 不足以授权删除目录。

## 8. 版本快照

### 8.1 v0.1 语义

版本快照是用户主动创建的、不可变的项目文件集合，类似 Overleaf 的 label，而不是完整 Git 替代品。

每个快照 MUST 具有：

- 唯一 ID。
- 用户可读标签。
- 可选说明。
- 创建时间。
- 文件清单、每个文件的大小与内容哈希。
- 快照时的主文件和 schema version。
- 完整性状态。

### 8.2 存储建议

v0.1 推荐在项目内部使用：

```text
<project>/.latex-editor/
├── project.json
└── versions/
    ├── index.json
    ├── blobs/
    │   └── <sha256>
    └── manifests/
        └── <snapshot-id>.json
```

内容寻址 blob 可避免相邻快照重复复制相同文件。实现更简单时可先使用每快照独立归档，但公开接口和 manifest 不应绑定具体存储方式。

快照 MUST 默认排除：

- `.latex-editor/versions/**`，避免递归快照。
- 常见编译中间产物。
- 项目配置定义的排除项。

排除规则来源必须是可编辑配置和带版本的默认资源，而不是散落在服务代码中的数组。安全所需的强制排除（例如版本存储自身）可以保留在代码中，并应在文档中标明。

### 8.3 版本接口

```ts
export interface VersionService {
  createSnapshot(input: CreateSnapshotInput): Promise<SnapshotSummary>;
  listSnapshots(projectId: string): Promise<SnapshotSummary[]>;
  getSnapshot(input: SnapshotRef): Promise<SnapshotManifest>;
  verifySnapshot(input: SnapshotRef): Promise<SnapshotVerification>;
  restoreSnapshot(input: RestoreSnapshotInput): Promise<RestoreResult>;
  deleteSnapshot(input: DeleteSnapshotInput): Promise<void>;
}
```

### 8.4 恢复规则

恢复是高风险覆盖操作。实现 MUST：

1. 校验 manifest 与所有 blob 哈希。
2. 计算恢复预览：将新增、覆盖和删除哪些文件。
3. 默认不执行，仅返回 preview；实际恢复要求 `confirmed: true`。
4. 恢复前自动创建一个 `pre-restore-<timestamp>` 安全快照，除非没有足够空间；空间不足时应中止而不是裸恢复。
5. 在项目内临时目录准备恢复内容，再尽可能原子地替换。
6. 不恢复或覆盖版本存储目录自身。
7. 任一步骤失败时返回结构化结果，并尽力保持原项目可用。

## 9. 数据驱动资源与禁止硬编码

### 9.1 强制要求

以下内容 MUST NOT 作为大型数组、switch/case 或对象字面量硬编码在 TypeScript 业务代码中：

- LaTeX 命令与参数元数据。
- 环境名称与 begin/end 行为。
- 补全词典。
- snippet 正文、占位符、说明和分类。
- 默认项目模板正文。
- 可配置的诊断匹配规则。
- 默认快照排除规则。
- 编译器 profile 的普通参数与显示信息。

这些内容必须存放在 `resources/` 下的 JSON、XML 或 SQLite 中，并带有 schema/version。v0.1 推荐：

| 数据类型 | 推荐格式 | 原因 |
|---|---|---|
| 命令、环境、snippet、模板清单 | JSON | 易校验、易 review、TypeScript 生态成熟 |
| 大型可查询索引 | SQLite | 适合搜索、去重、增量更新 |
| 需要与外部 TeX/XML 数据互操作的词典 | XML | 保留层级和外部兼容性 |
| 项目注册表 | SQLite | 唯一约束、迁移和查询可靠 |

“不得硬编码”不代表把业务逻辑放入配置。路径安全规则、状态机、权限判断、哈希校验和参数 allowlist 等逻辑 MUST 留在代码中。

### 9.2 资源加载层级

资源解析优先级 SHOULD 为：

```text
project override > user override > packaged defaults
```

合并规则必须确定且有测试。每个资源文件 MUST：

- 声明 `schemaVersion`。
- 在使用前通过 JSON Schema、XSD 或数据库约束验证。
- 解析失败时报告文件位置和字段路径。
- 不得执行代码、表达式或任意 shell 命令。
- 支持稳定 ID，以便覆盖和禁用默认项。

### 9.3 示例：命令资源

```json
{
  "$schema": "../schemas/commands.schema.json",
  "schemaVersion": 1,
  "commands": [
    {
      "id": "latex.section",
      "name": "section",
      "insertText": "\\section{${1:title}}",
      "detail": "Section heading",
      "category": "structure",
      "arguments": [
        { "kind": "required", "name": "title" }
      ]
    }
  ]
}
```

### 9.4 示例：环境资源

```json
{
  "$schema": "../schemas/environments.schema.json",
  "schemaVersion": 1,
  "environments": [
    {
      "id": "latex.environment.figure",
      "name": "figure",
      "begin": "\\begin{figure}[${1:htbp}]",
      "body": "  ${2}",
      "end": "\\end{figure}",
      "category": "float"
    }
  ]
}
```

### 9.5 Resource Catalog 接口

```ts
export interface ResourceCatalogService {
  reload(scope?: ResourceScope): Promise<ResourceLoadReport>;
  searchCommands(query: string, context?: CompletionContext): Promise<CommandMetadata[]>;
  searchEnvironments(query: string): Promise<EnvironmentMetadata[]>;
  listSnippets(context?: CompletionContext): Promise<SnippetMetadata[]>;
  getTemplate(templateId: string): Promise<ProjectTemplate>;
}
```

资源加载失败时，应用 SHOULD 继续使用上一次验证成功的 catalog；首次启动且默认资源无效时必须快速失败，并给出可操作的错误信息。

## 10. Electron IPC 合同

IPC contract MUST 定义在独立 `packages/contracts` 中，并由 main、preload 和 renderer 共同引用。

建议 preload 暴露：

```ts
export interface LatexEditorApi {
  projects: {
    list(): Promise<ProjectSummary[]>;
    registerFolder(input: RegisterFolderInput): Promise<Project>;
    open(projectId: string): Promise<Project>;
    remove(input: RemoveProjectRequest): Promise<RemoveProjectResult>;
  };
  documents: {
    open(input: OpenDocumentInput): Promise<OpenDocument>;
    applyChanges(input: ApplyTextChangesInput): Promise<OpenDocument>;
    save(input: SaveDocumentInput): Promise<SaveDocumentResult>;
  };
  compiler: {
    compile(input: CompileInput): Promise<CompileResult>;
    cancel(compilationId: string): Promise<CancelResult>;
  };
  versions: {
    create(input: CreateSnapshotInput): Promise<SnapshotSummary>;
    list(projectId: string): Promise<SnapshotSummary[]>;
    previewRestore(input: SnapshotRef): Promise<RestorePreview>;
    restore(input: RestoreSnapshotInput): Promise<RestoreResult>;
  };
}
```

所有 IPC 输入 MUST 在 main process 边界做运行时 schema 校验，不能只依赖 TypeScript 类型。错误应序列化为稳定结构：

```ts
export interface AppErrorPayload {
  code: string;
  message: string;
  details?: Record<string, unknown>;
  retryable: boolean;
}
```

不得向 renderer 泄露绝对路径以外的敏感环境信息、堆栈或任意系统对象。开发模式可把完整堆栈写入本地日志。

## 11. CLI 调试规格

### 11.1 目的

CLI 是 v0.1 的正式调试入口，不是一次性脚本。它必须调用 application service，并以退出码和可选 JSON 输出支持自动化。

### 11.2 命令建议

```text

latex-editor file write <project-id> <relative-path> --stdin [--force]
```

### 11.3 CLI 行为

- 成功退出码为 `0`。
- 用户输入/校验错误为 `2`。
- 编译失败为 `3`。
- 工具链缺失为 `4`。
- 文件冲突为 `5`。
- 内部错误为 `1`。
- `--json` 时 stdout MUST 只输出单个稳定 JSON 文档；人类日志写入 stderr。
- 非交互环境不得弹出 Electron 窗口或系统选择器。
- 所有危险操作默认 non-interactive fail；必须提供完整确认参数。

## 12. 自动化测试策略

### 12.1 测试层级

| 层级 | 目标 | 是否需要真实 `latexmk` |
|---|---|---:|
| 单元测试 | 状态机、路径校验、解析器、资源合并 | 否 |

具体测试框架可替换，但必须保留等价的一键验证命令。

### 14.2 真实 `latexmk` 测试的处理

- `test:compiler` 启动前先调用 toolchain detection。
- 本地没有 `latexmk` 时，可将真实编译组标记为 skipped，但单元/集成测试不得因此跳过。
- CI 至少有一个 job 安装固定的大版本 TeX 发行版并运行真实编译测试。
- 测试报告必须明确区分 pass 与 skip，不能把缺少工具链显示为成功验证。
- 诊断 parser 必须另有固定日志 fixture 测试，因此即使本机无 LaTeX 也能验证解析逻辑。

### 14.3 覆盖率与质量门槛

v0.1 建议最低门槛：

- domain/application/editor-core/diagnostics 行覆盖率 ≥ 85%。
- path safety、删除策略、恢复策略分支覆盖率 ≥ 90%。
- 所有公开 contract 至少有一个成功用例和一个失败用例。
- 不以 snapshot test 代替关键业务断言。
- 时间、绝对路径、随机 ID 必须规范化后再做快照断言。

## 16. 可观察性与日志

- 使用结构化日志，并带 `operationId`/`compilationId`。
- 日志不得写入文档完整正文、环境变量全集或用户密钥。
- 关键动作记录：项目注册/移除、编译开始/结束、快照创建/校验/恢复、资源加载。
- 开发模式保留 stack trace；用户可见结果只返回稳定错误结构。
- 编译日志属于项目产物，可配置保留数量；应用日志写入 Electron `userData` 下的日志目录。
- CLI `--verbose` 可提高日志级别，但不得破坏 `--json` stdout 合同。

## 17. 兼容性与平台要求

v0.1 至少以 Windows 为首要支持平台，同时保持 Node 路径 API 的跨平台写法：

- 禁止用字符串拼接路径分隔符。
- 测试包含空格、非 ASCII 字符和长路径场景。
- canonical path 比较应封装为平台策略。
- 进程取消需终止 `latexmk` 派生的进程树；Windows 与 POSIX 使用不同 adapter。
- SQLite driver 必须与 Electron/Node ABI 构建流程兼容，或选择不依赖原生 ABI 的受支持方案。

## 18. v0.1 验收标准

只有以下条件全部满足，v0.1 核心才可视为完成：

1. `npm run verify` 或等价命令一次通过。
2. CLI 可在无 Electron renderer 的环境中完成“创建/注册项目—编辑文件—编译—查看诊断—创建快照—恢复快照”的闭环。
3. 至少一个成功项目与三个失败/警告 fixture 通过真实 `latexmk` 验证。
4. 外部文件修改不会被默认保存静默覆盖。
5. “只移除注册”测试证明本地目录及内容完全不变。
6. “删除本地文件夹”必须经过路径完全匹配确认，危险根路径测试全部被拒绝。
7. 快照恢复前会生成安全快照，损坏快照无法恢复。
8. 补全、snippet、命令、环境和模板内容可仅通过修改资源文件改变，并通过 schema 验证；业务代码中不存在对应的大型硬编码表。
9. Core packages 不依赖 Electron、React 或 Monaco。
10. Renderer 无 Node 全权限，所有 IPC 输入经过运行时校验。
11. SQLite migration 可从空数据库稳定创建当前 schema，并可重复启动而不破坏数据。
12. README 说明本地开发、安装/检测 `latexmk`、运行 CLI、运行全部测试和常见失败排查方法。

## 19. 实现顺序建议

按以下顺序实现，可最早获得可调试闭环：

1. 建立 workspace、contracts、错误模型与测试基础设施。
2. 实现项目 registry、路径安全和 project/file service。
3. 实现 DocumentService 状态机与原子保存。
4. 实现 Resource Catalog、schema 和最小命令/环境/snippet 数据。
5. 实现 `latexmk` adapter、取消/超时和 DiagnosticService。
6. 实现 VersionService、manifest、校验、preview 与安全恢复。
7. 实现 CLI 并覆盖 E2E。
8. 最后接入 Electron preload/IPC 与最薄的 Monaco adapter。

每一步都应先提供测试，再暴露给下一层；不要先写 renderer 再把业务逻辑向外抽取。

## 20. 后续扩展点

当前 contract 应为以下能力留出空间，但不得提前把 v0.1 复杂化：

- LSP 或更完整的 LaTeX AST parser。
- BibTeX/Biber 数据库索引与引用预览。
- SyncTeX 正反向定位。
- 多编译器 profile：pdfLaTeX、XeLaTeX、LuaLaTeX、Tectonic。
- 后台增量索引、文件 watcher 和大型项目性能优化。
- Git-backed 版本服务 adapter；保持 `VersionService` contract 不变。
- 快照导出/导入、压缩、垃圾回收和配额管理。
- 项目模板市场和用户资源包。
- 插件 API；插件仅通过受限 capability 调用核心服务。
- 云同步与远程项目；本地项目仍是独立 adapter。
- 国际化 UI 和错误消息；稳定 error code 保持不变。
- PDF viewer、增量刷新和编译产物管理。

## 21. Codex 实施约束清单

Codex 在实现时 MUST 遵守：

- 不把核心逻辑写进 React component、IPC handler 或 CLI command handler。
- 不在 renderer 使用 Node 文件系统或启动进程。
- 不将补全、snippet、命令、环境、模板数据硬编码到 TypeScript。
- 不使用 `shell: true` 调用 `latexmk`。
- 不在没有完全匹配确认路径时删除项目目录。
- 不静默覆盖外部修改过的文件。
- 不在恢复快照前跳过校验、preview 和安全快照。
- 不把测试指向用户真实目录。
- 不提交编译产物、临时数据库、测试临时目录或真实用户路径。
- 每完成一个模块，同时提交其 contract、实现、错误码和自动化测试。

## 22. Definition of Done 模板

每个实现任务完成时，应在交付说明中回答：

```text
- 实现了哪些公开接口？
- 数据保存在哪里，schema/version 是什么？
- 哪些内容是资源驱动的？对应 schema 在哪里？
- 添加了哪些测试用例 ID？
- 实际运行了哪些验证命令，结果如何？
- 是否需要 latexmk；未安装时哪些测试被 skip？
- 有哪些已知限制或后续工作？
- 是否涉及覆盖、删除或恢复等危险操作；安全机制是什么？
```

以上答案和自动化测试结果共同构成 v0.1 的可审查交付证据。
